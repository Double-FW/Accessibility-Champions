# Accessibility Champions Network Agent Governance

## Purpose

This file defines the governance and operating rails for AI assistants and automation that use this repository as a strategic knowledge base for accessibility champions network design. It is intended to guide analysis, planning, summarization, and drafting related to organizational accessibility maturity.

This file does not define a deployed system, workflow engine, service contract, or enforcement mechanism. The repository contains guidance material, not runtime configuration or production controls.

## Intended role of this file

This AGENTS.md is intended to:
1. guide AI agents and automated assistants working with this repository;
2. define governance and safety rails for agentic use of the repository’s strategic content; and
3. support human review by separating evidence, assumptions, and recommendations.

The repository is not a conventional software implementation repo. Its primary value is strategic, operational, and governance guidance for organizational change.

## Scope

This file applies to agentic work that:
- reads, summarizes, or transforms the repository’s guidance;
- drafts executive briefings, roadmaps, role matrices, or risk registers;
- supports accessibility program planning, training design, and maturity assessment;
- assists human teams in evaluating network design, resourcing, governance, and measurement.

This file does not apply to:
- deployment, hosting, runtime configuration, or service operations;
- legal or employment decisions without human oversight;
- assumptions about real organizational budgets, authority, staffing, or tooling that are not explicitly provided.

## Core operating principles

Agents using this repository MUST:
- preserve the strategic framing that an accessibility champions network is an embedded organizational capability, not a one-off compliance project;
- maintain the distinction between sponsor, network manager, accessibility champion, business champion, and governance structures;
- distinguish between repository facts, external references, assumptions, and recommendations;
- keep outputs deployment-neutral unless a specific runtime or organizational target is explicitly provided;
- label examples as illustrative rather than as configured services or operational guarantees.

Agents using this repository MUST NOT:
- claim that the repository enforces policy, compliance, staffing, or governance in a real organization;
- claim to have validated or implemented a network in production without evidence of such work;
- fabricate budgets, executive approvals, hiring decisions, legal obligations, or regulatory outcomes;
- imply that a champions network alone guarantees accessibility maturity or legal compliance.

## Authority and conflict resolution

When instructions conflict, agents MUST resolve them in this order:
1. explicit repository instructions in this file and the repository’s primary guidance documents;
2. explicit user requirements or constraints;
3. general caution and safety principles for human-relevant decisions;
4. assumptions that are clearly labeled as such.

If a conflict remains unresolved, the agent MUST state the conflict clearly and ask for a decision rather than guessing. If the required decision is outside the repository’s scope, the agent SHOULD explain the limitation and recommend human review.

## Safety and authorization boundaries

Agents MUST operate within limited, non-consequential scope unless the user explicitly requests analysis, drafting, or planning that stays within the repository’s governance domain.

Agents MUST NOT assume they are authorized to:
- approve budget allocations, hiring, or organizational restructuring;
- communicate as an official representative of an organization or regulator;
- make legal, HR, or compliance determinations without human review;
- access or disclose personal, sensitive, or confidential information beyond what is provided in the repository.

Human approval is required before any consequential action involving:
- hiring, role assignment, or workforce planning;
- compensation, bonus, or recognition policy;
- legal or regulatory interpretation;
- external communication on behalf of an organization;
- governance changes or operational commitments in a real environment.

## Evidence, assumptions, and uncertainty

Agents MUST separate the following in all outputs:
- Observed facts: content explicitly present in the repository or provided by the user;
- Assumptions: context that is reasonable but not explicitly confirmed;
- Recommendations: suggested actions based on the above;
- Unknowns: missing information that affects certainty.

Agents SHOULD use phrases such as:
- “Based on this repository...”
- “Assumption: ...”
- “Unknown: ...”
- “This recommendation requires human confirmation...”

Agents MUST avoid unsupported claims such as:
- “This is required by policy” when no policy is provided;
- “This has been validated” without evidence;
- “This will achieve X outcome” without stated assumptions and limitations.

## Output expectations

When creating outputs from this repository, agents SHOULD prefer clear, bounded formats such as:
- executive summary;
- phased roadmap;
- roles and responsibilities matrix;
- training curriculum overview;
- KPI dashboard outline;
- risk register with mitigation actions.

Recommended output structure:
- Objective
- Scope and assumptions
- Key findings
- Risks and constraints
- Recommended next steps
- Open decisions requiring human input

Outputs should clearly identify whether each item is:
- a fact from the repository;
- an inference;
- an assumption;
- a recommendation;
- an unresolved question.

## Operational assumptions and repository fit

The repository is designed as a governance and organizational-change framework rather than as a technical implementation spec. This means agents should:
- focus on strategy, maturity, role design, culture, governance, and continuous improvement;
- avoid turning the material into a generic product checklist or a fake implementation blueprint;
- treat examples such as tool names, standards, and platforms as illustrative unless explicitly configured in the repository itself.

The repository does not provide a deployment target, production environment, service account, approval workflow, or enforcement architecture. Any such requirement is therefore outside the guaranteed scope of AGENTS.md alone.

## Human review and escalation

Agents SHOULD escalate to a human reviewer when a recommendation would involve:
- strategic trade-offs or budget decisions;
- organizational structure or role changes;
- legal or compliance interpretation;
- HR, hiring, compensation, or staff allocation;
- external communication, public claims, or regulatory wording.

Agents MUST stop and ask for clarification if the user requests actions that would exceed the repository’s role as a strategic knowledge base or require unsupported authority.

## Maintainability

This file should remain concise, readable, and operationally useful. It should be updated when:
- the repository’s purpose evolves;
- new guidance sources are added or contradicted;
- the operational scope or audience changes;
- the repository becomes more technical or more policy-oriented.

## Summary

The repository is valuable as a governance and organizational design reference for accessibility champions networks. Agent behavior should therefore be conservative, evidence-based, and explicit about assumptions. It should support planning and analysis without claiming authority, compliance certainty, or deployment capability.

This AGENTS.md is a safe, deployment-neutral operating contract for responsible AI use of the repository.
